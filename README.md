# Между строк

Читает ТЗ и достаёт невысказанные ожидания заказчика: требования, объём
в часах, красные флаги, вопросы до старта. Второй режим проверяет готовую
работу перед сдачей — так же, как её посмотрит принимающий.

## Зачем

Человек не проговаривает то, что для него очевидно.

Заказчик не пишет в брифе «сделай аудит с выводами» — он так работает каждый
день, для него это воздух. Босс не объясняет контекст, в котором живёт
с понедельника. Получатель этого не видит, делает ровно по написанному
и промахивается.

## Работает ли это

Да, и это проверено на реальном случае.

Дизайнер выполнила тестовое задание для инвестиционного брокера. В брифе было
четыре предложения. Она вложилась всерьёз — исследование, анализ конкурентов,
научные статьи, калькулятор тарифа — и получила отказ на одиннадцать пунктов,
**ни одного из которых в задании не было**.

«Между строк» получил только бриф. Письмо с отказом ему не показывали.

| | |
|---|---|
| Точных попаданий | **8 из 11** |
| Задето частично | 2 |
| Не увидел | 1 |

Несколько совпадений почти дословные:

> **Заказчик:** «Предлагать — хорошо, только подкрепляй гипотезой: зачем это
> бизнесу и что изменится, если добавить.»
>
> **Приложение, заранее:** «Любую добавленную сущность вносить только с явной
> пометкой „гипотеза" и одной строкой: зачем бизнесу и какая метрика изменится.»

Разбор выполнял отдельный агент с доступом ровно к двум файлам — методике
и тексту брифа. Разбирающий, который уже видел письмо, подогнал бы ответ
и не заметил этого, поэтому проверка только вслепую.

Полная сверка: [`cases/go-invest/score.md`](cases/go-invest/score.md).
Второй кейс — корпоративный интерфейс вместо маркетинговой страницы, проверка
на то, что механизмы не привязаны к жанру: [`cases/sber-b2e/`](cases/sber-b2e/).

## Что выдаёт

Два режима одного инструмента: разбор задания перед тем, как берёшься,
и проверка готовой работы перед тем, как её сдать.

На входе: само задание (текст, ссылка или файл), сайт компании, вакансия,
резюме — а в режиме проверки ещё и сама работа. Обязательно только задание
(при проверке — работа), остальное по желанию.

**Разбор задания** — тестовое, ТЗ, письмо от начальника, условия вакансии.

1. Стоит ли браться — объём в часах, влезает ли в срок, признаки того, что
   на исполнителе собирают бесплатную работу
2. Что просят буквально
3. Чего в брифе нет, но спросят — главный блок
4. Как это будут оценивать
5. Красные флаги
6. Что спросить до старта — готовыми формулировками
7. Что показать при сдаче, кроме основного результата

**Проверка работы** — та же работа, уже сделанная, до отправки.

1. Что уже закрыто
2. Чего не хватает — главный блок
3. За что срежут первым делом
4. Что дописать перед сдачей, с оценкой в часах
5. Как это прочтут

Выдача идёт разделами; сверху — шкала (часы на задание или закрытые ожидания
на проверке) и плитки с ключевыми числами.

## Как устроено

Продукт — это `core/analysis.md` и `core/review.md`: девять механизмов
(М1–М9), по которым невысказанное пропадает из текста. Не чеклист (устареет
на втором кейсе), а причины.

Например: «решать тебе» означает, что судят ход мысли, а не результат.
Названный сегмент («состоятельные клиенты») означает проверку на фактическую
достоверность — одна неверная деталь обнуляет доверие ко всей работе.
Перечисленный состав услуги — это границы, и всё сверх него требует гипотезы.

Незнакомую область приложение сначала выясняет через поиск, потом разбирает.
Каждый пункт помечен: **надёжно** (из механизма, верно везде), **нашёл**
(со ссылкой на источник) или **проверь сам**.

Единственное, чего поиск не даёт, — привычки конкретной компании: они нигде
не опубликованы. Их предсказывают механизмы.

```
core/analysis.md      разбор задания — механизмы М1–М9
core/review.md        проверка готовой работы перед сдачей
cases/                эталонные кейсы и сверка с реальными отказами
api/analyze.js        Claude Opus 5, веб-поиск, ответ стримом
public/               страница приложения и страница с проверкой
.claude/              скилл разбора и агент для слепой проверки
```

## Запуск у себя

Приложение работает на вашем ключе Anthropic и тратит ваши деньги — своего
сервера у него нет и приёма платежей тоже.

```bash
git clone https://github.com/<ваш-аккаунт>/mezhdu-strok.git
cd mezhdu-strok
npm install
cp .env.example .env      # вписать свой ключ Anthropic
node dev.mjs              # откроется на http://localhost:3000
```

Ключ берётся на [console.anthropic.com](https://console.anthropic.com/settings/keys),
там же пополняется баланс. В коде ключей нет и быть не должно — только
переменные окружения; `.env` в `.gitignore` и в репозиторий не попадает.

**Сколько это стоит.** Разбор задания — примерно $0,25–0,30 и две-три минуты,
проверка готовой работы — около $0,15. Цена зависит от длины задания и от того,
пришлось ли приложению искать нормы незнакомой профессии в интернете.
Проверить всё, кроме живого разбора, можно бесплатно: `node test-files.mjs`
не обращается к API вовсе.

Есть и второй способ — без интерфейса, прямо в Claude Code: скопируйте
`.claude/skills/razbor/` и `core/` к себе в проект и скажите «разбери это ТЗ».
Тогда платите за обычную сессию, а не за отдельные вызовы.

## Ограничения

Разбор — версия, а не приговор: заказчик может думать иначе. В незнакомых
областях предметная конкретика слабее, и такие пункты помечены «проверь сам».
Оценка объёма в часах надёжна там, где есть на что опереться — дизайн,
разработка, тексты, маркетинг, аналитика; в остальных случаях выдаётся
не цифра, а список частей работы.
